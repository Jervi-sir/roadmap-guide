React Mindset

start here

Start with TypeScript right away — no worries if it feels strict at first, it's the only way to build reliable apps in 2026.

Learn React itself — components, props, state, and JSX. That's your foundation.

Skip design patterns (MVC, Observer, Factory, etc.) — they are useless at this stage. Focus on building things, not architecture theory.

Always think about making reusable components — if you write a button in two places, extract it into a shared component that accepts props.

💡 Keep it simple Don't over-engineer. Build first, refactor later when you actually see repeated patterns.

Component Philosophy

core rule

Dumb components = no logic inside them. They receive props (params) and render UI. That's it.

Parent holds the logic. The parent page/component handles state, data fetching, and event handlers — then passes everything down as props.

Think reusable first — a component that accepts props can be used anywhere. Write once, use everywhere.

// ✅ Dumb component — no logic, only props
function ProductCard({ title, price, onBuy }) {
return (
<div>
<h3>{title}</h3>
<p>{price}</p>
<button onClick={onBuy}>Buy</button>
</div>
);
}
// ✅ Parent holds all the logic
function StorePage() {
const [products] = useState([...]);
const handleBuy = (id) => { /* logic here */ };
return products.map(p =>
<ProductCard title={p.title} price={p.price} onBuy={() => handleBuy(p.id)} />
);
}

Hooks — Don't Overdo It

⚠ warning

Don't abuse useHooks — extracting everything into custom hooks makes code harder to read and chaotic to debug.

If the logic is only used in one page, just write it directly inside that page component. No need to extract it.

Only create a custom hook when the exact same logic is genuinely reused in multiple places.

⚠ Anti-pattern Creating useFormInput, useToggle, useLocalStorage for one-off logic just adds indirection. Keep it simple — write it inline.

API Layer — Write once, use everywhere

pattern

Use Axios for all API calls. Create one wrapper function (e.g. api.ts) that handles everything.

Inside the wrapper: read the Bearer token from localStorage and attach it to every request automatically. Write once, every request is authenticated.

Every API call in your app goes through this function — never raw fetch() or axios.get() directly in components.

Save the bearer token in localStorage after login: localStorage.setItem('token', ...). Done.

// lib/api.ts — write once, use everywhere
import axios from 'axios';
const api = axios.create({
baseURL: 'https://your-api.com',
});
// Auto-attach Bearer token to every request
api.interceptors.request.use((config) => {
const token = localStorage.getItem('token');
if (token) config.headers.Authorization = `Bearer ${token}`;
return config;
});
export default api;
// Usage anywhere: api.get('/users'), api.post('/orders', data)

Next.js — When you're comfortable with React

next level

Once you're comfortable with React + everything mentioned above → move to Next.js. You need it to learn database setup and middleware.

Database ORM: use Drizzle — it's better than Prisma (lighter, faster, SQL-like syntax you can actually understand).

Middleware in Next.js: just create a middleware.ts file at the project root — Next.js auto-detects it. No config needed.

⚠ Next.js middleware limitation Unlike Laravel where you can have many middleware files with full flexibility, Next.js only supports one middleware.ts file. You handle all middleware logic (auth checks, redirects, etc.) inside that single file with conditionals. For most use cases this is totally fine.
// middleware.ts — at project root
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';
export function middleware(request: NextRequest) {
const token = request.cookies.get('token');
if (!token) return NextResponse.redirect('/login');
return NextResponse.next();
}
// Which routes to protect
export const config = {
matcher: ['/dashboard/:path*', '/api/:path*'],
};

Supabase — Auth + Database in one

recommended

Use Supabase for auth — it gives you Google, GitHub, email/password login out of the box. No need to set up NextAuth or write auth logic from scratch. One supabase.auth.signInWithOAuth() call and you're done.

Use Supabase for your database — it's a hosted PostgreSQL instance with a beautiful dashboard. You get a real Postgres DB, but without the pain of setting it up yourself. Create tables, add columns, set up relations — all from the UI or with SQL.

Row Level Security (RLS) — Supabase lets you write security rules directly on the database. Example: "users can only read their own rows." This means even if your API has a bug, the data is still protected at the DB level.

Free tier is generous — 500MB database, 50,000 monthly active users for auth, 1GB file storage. More than enough to build and launch real projects without paying a cent.

You can still use Drizzle ORM with Supabase — just point Drizzle's connection string to your Supabase Postgres URL. Best of both worlds: Supabase for hosting + auth, Drizzle for type-safe queries.

// lib/supabase.ts — setup once
import { createClient } from '@supabase/supabase-js';
export const supabase = createClient(
process.env.NEXT_PUBLIC_SUPABASE_URL!,
process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
);
// Sign in with Google — one line
await supabase.auth.signInWithOAuth({
provider: 'google'
});
// Get current user
const { data: { user } } = await supabase.auth.getUser();
// Query your DB (or use Drizzle instead)
const { data } = await supabase.from('tasks').select('*');
✅ Use Supabase when Starting a new project, need auth fast, want a hosted DB without server setup, building with Next.js, or prototyping an MVP.
⚠ Use your own DB when You need full control (custom VPS), you're building a standalone backend with Fastify, or you want to learn raw PostgreSQL setup for experience.

Architecture: Domain-Driven Design

DDD

Yes, use MVC — but I prefer you go further with Domain-Driven Design. It keeps your project modular and clean as it grows.

Put your models in one folder, your views in one folder — but for controllers, group them by domain (not by type). Each domain gets its own folder with its own routes.

Example: a Product/ folder contains all controllers related to Product — Product as Buyer, Product as Supplier, Product as Admin. You won't find a Profile controller inside the Product folder.

This way you get a modular project — if it's a collab coding project, each developer can work on their own domain folder without conflicts. Way less merge issues.

💡 Real talk Sometimes you'll break the architecture — that's normal. The point is to have a default structure you follow. It's about being consistent 90% of the time, not 100%.

Suggested Folder Structure — Node.js (Fastify)

src/
├── domains/ // each domain is self-contained
├── product/
├── product.routes.ts // GET /products, POST /products
├── product.controller.ts // handles request/response
├── product.service.ts // business logic
└── product.schema.ts // validation (Zod/Typebox)
├── user/
├── user.routes.ts
├── user.controller.ts
├── user.service.ts
└── user.schema.ts
└── order/
└── ...
├── models/ // Drizzle DB schemas (shared)
├── middlewares/ // auth, rate-limit, etc.
├── plugins/ // Fastify plugins (DB, Redis)
├── utils/ // helpers, formatters
├── app.ts // Fastify app setup
└── server.ts // start the server
📁 Why this structure? Each domain folder is independent — you can delete or refactor a whole domain without touching others. When a teammate is working on order/, they won't conflict with your work on product/.

Queues — When You Need Them

Queues are for long-running tasks that you don't want to block the user for — video compression, waiting for AI to respond, sending emails, processing payments.

The idea: user makes request → you push to queue → respond immediately with "processing" → a background worker handles the heavy task.

Without queues, the user stares at a loading spinner for 30 seconds while your server compresses a video. With queues, they get instant feedback.

Use Redis (BullMQ) or the queue provided by Postgres. Both work great with Node.js.

Monitoring & Visibility

Use Hono Telescope for a real-time dashboard of your requests, performance, and server health. It's like X-ray vision for your API.

Pair Uptrace + Pino for structured logging and distributed tracing. Uptrace gives you a clean UI to track every request from frontend to DB.

💡 observability is key Don't wait for users to complain. With this stack, you'll see errors and bottlenecks before they do.

VPS Setup — Hetzner

$5/month

Buy a Hetzner Ubuntu VPS (~$5/mo). Best price/performance ratio out there.

Use AI to help you set up the server. Tell it: "I have a Hetzner Ubuntu VPS, I want to create a new user and password, and allow SSH with password." It'll give you the exact commands.

You can SSH from VSCode directly into the server — install the "Remote - SSH" extension and you'll be coding on the server as if it's your local machine.

Step-by-step Deployment

1

Ports (UFW)

Learn ports using UFW (Uncomplicated Firewall). When you want to host your backend, you need to open the port it runs on so the internet can access it.

Install UFW, then immediately run ufw allow 22 — this allows SSH. If you enable UFW without this, you're locked out forever. Then open your app port: ufw allow 3000 (or whatever port your backend uses).

2

Domain Name

Buy a domain on Namecheap. Then go to Advanced DNS settings in Namecheap.

Add an A Record: set the host to @ (for root domain) and put your Hetzner server's IP address as the value. Now your domain points to your server.

3

Nginx (Reverse Proxy)

Install Nginx and use AI to configure it. Tell AI: "I have this domain name [yourdomain.com], I want to serve it over port [your port], also set the max file upload size to 1GB."

Nginx sits in front of your Node.js app and routes traffic from port 80/443 (HTTP/HTTPS) to your internal app port (e.g. 3000).

4

SSL (HTTPS)

Use Certbot (it's a Python library) to get free SSL. It auto-configures Nginx for HTTPS. One command and your site is secure. Don't forget to also open the port your backend uses with UFW.

5

PM2 (Keep it alive 24/7)

Install PM2 — it's a process manager built for Node.js. It keeps your backend running 24/7, auto-restarts on crash.

Use AI here too — tell it: "Generate an ecosystem.config.js for PM2, tell it my port is [your port], use fork mode (not cluster), and show me how to start it."

Once running, use pm2 status to see all your running processes. Use pm2 logs to debug issues.

UFW Critical Warning

Always ufw allow 22 BEFORE enabling UFW. Miss this = can't SSH back in. No recovery. You'll have to reinstall the entire VPS from scratch.

Database Choices

Hosted DB + Auth Supabase ✓
DB Engine PostgreSQL
ORM Drizzle
Cache Redis
💡 Supabase = PostgreSQL Supabase is PostgreSQL — it's not a different database. It's a hosted Postgres with a dashboard, auth system, and storage built on top. Everything you learn in Supabase applies to raw PostgreSQL.

Why Supabase + Drizzle?

Supabase handles hosting, auth, storage, and gives you a real Postgres URL.

Drizzle connects to that URL and gives you type-safe, SQL-like queries. Lighter and faster than Prisma.

Auth is built-in — Supabase Auth gives you Google, GitHub, email/password, magic links. No need to build auth from scratch.

RLS (Row Level Security) — write DB-level rules like "users can only see their own data." Extra layer of protection even if your API code has bugs.

Build These Projects

The best way to learn is by building. Here are 4 projects ordered by difficulty — each one teaches you something new. Follow the steps in order, and don't skip ahead.

1

Task Manager App

beginner

A full CRUD app with auth. This covers 80% of what real apps need. You'll learn the entire flow from UI to database to deployment.

Step 1

Run npx create-next-app@latest with TypeScript enabled. Install Tailwind CSS and shadcn/ui for your component library. This is your project skeleton.

Step 2

Build the UI first with no backend — create a task list component, an "add task" form with shadcn Input + Button, an edit modal using shadcn Dialog, and a delete confirmation. Use hardcoded dummy data for now.

Step 3

Install PostgreSQL locally (or use a free Neon/Supabase DB). Set up Drizzle ORM — define a tasks table with columns: id, title, description, status (todo/done), userId, createdAt. Run your first migration.

Step 4

Create Next.js API routes inside app/api/tasks/ — implement GET (list all), POST (create), PUT (update status/title), DELETE (remove). Connect each route to Drizzle queries. Test with Postman or Thunder Client.

Step 5

Add Supabase Auth — set up Google and/or GitHub OAuth with supabase.auth.signInWithOAuth(). Use Supabase's middleware.ts helper to protect all /dashboard routes. Enable RLS so users only see their own tasks.

Step 6

Add Zod validation on every API route — validate title length (min 1, max 100), status must be "todo" or "done", userId must match session. Never trust client input. Return proper error messages.

Step 7

Deploy to Hetzner VPS — set up Ubuntu server, install Node.js, clone your repo with Git, configure Nginx as reverse proxy, get SSL with Certbot, run your app with PM2. Your first live app on the internet 🎉

2

Password Manager

beginner+

A secure vault for passwords. This teaches you encryption, master-password auth, clipboard APIs, and how to think about security from day one.

Step 1

Set up Next.js + Drizzle + PostgreSQL. Design the DB schema: a vaults table (id, userId, masterPasswordHash) and a credentials table (id, vaultId, siteName, siteUrl, username, encryptedPassword, createdAt).

Step 2

Implement master password flow — on first login, the user creates a master password. Hash it with bcrypt and store the hash. Every session requires re-entering it. Never store the raw password.

Step 3

Learn AES-256 encryption — use the master password to derive an encryption key (with crypto.pbkdf2). Encrypt each password before saving to DB, decrypt on read. The server never sees plaintext passwords.

Step 4

Build the vault UI — a searchable list of saved credentials with site name, username (visible), and password (hidden by default). Add a "copy password" button that uses navigator.clipboard.writeText().

Step 5

Add a password generator — let users generate random passwords with options for length, uppercase, lowercase, numbers, symbols. Show a strength indicator (weak/medium/strong).

Step 6

Add auto-lock — after 5 minutes of inactivity, clear the decryption key from memory and force re-entering the master password. Use setTimeout with activity listeners.

Step 7

Add Zod validation on all inputs + rate limiting on the master password endpoint (max 5 attempts per minute). This prevents brute-force attacks.

Step 8

Deploy securely — Hetzner VPS with Nginx + SSL (HTTPS is mandatory for a password app). Set secure HTTP headers, enable HSTS, and use PM2 to keep it running 24/7.

3

E-Commerce Store

intermediate

A real store with products, cart, checkout, and payment. This teaches you how money flows in apps, how to handle orders, and how to build admin tools.

Step 1

Design the DB schema in Drizzle — products (id, name, price, image, stock, categoryId), orders (id, userId, total, status), order_items (orderId, productId, qty, price). Think about relationships.

Step 2

Build the product listing page — responsive grid with product cards (image, name, price, "Add to Cart" button). Add category filters and a search bar. Use Zustand to manage the cart state across pages.

Step 3

Create a centralized Axios API layer in lib/api.ts — auto-attach Bearer token from localStorage, set baseURL, handle 401 errors globally (redirect to login). Every component uses this, never raw fetch().

Step 4

Build the checkout flow as a multi-step form — Step 1: cart summary with quantity controls. Step 2: shipping address form with Zod validation. Step 3: order review + "Place Order" button that creates the order in DB.

Step 5

Integrate Stripe for payment — use Stripe Checkout (hosted page) for simplicity. Create a /api/checkout route that creates a Stripe session. Handle the checkout.session.completed webhook to mark orders as paid.

Step 6

Build order tracking — create an orders page showing all user orders with status badges (pending → paid → shipped → delivered). Use colored badges from shadcn. Add real-time status updates if you want to get fancy.

Step 7

Build an admin dashboard — separate /admin routes protected by role-check middleware. Features: add/edit/delete products, view all orders, update order status, see total revenue.

Step 8

Deploy with DDD structure — organize your backend into domain folders: product/, order/, user/. Each domain has its own routes, controller, service, and schema. Deploy to Hetzner.

4

SaaS App with Subscriptions

advanced

A multi-user platform with billing, dashboards, and background jobs. This is what real startups build. If you can build this, you can build anything.

Step 1

Build a landing page that sells — hero section with a clear value prop, feature grid with icons, a pricing table (Free / Pro / Business tiers), FAQ accordion, and a sign-up CTA. Make it look like a real product.

Step 2

Set up multi-tenant auth — users register, then create or join an organization. DB schema: users, organizations, memberships (userId, orgId, role). Each org has its own data.

Step 3

Integrate Stripe Subscriptions — create products + prices in Stripe Dashboard. Use Stripe Checkout for subscribing. Handle webhooks: customer.subscription.created, .updated, .deleted to sync plan status to your DB.

Step 4

Build a user dashboard — show current plan, usage metrics (API calls, storage used), billing history from Stripe, and a "Manage Subscription" button that opens Stripe's Customer Portal.

Step 5

Add background jobs with BullMQ + Redis — create a job queue for email sending (welcome, invoice, password reset), weekly report generation (aggregate data into PDF), and any AI processing tasks. Show job status in the UI.

Step 6

Add Hono Telescope + Uptrace + Pino — Telescope gives you a real-time request dashboard. Pino handles structured JSON logging. Uptrace collects traces so you can see the full lifecycle of every request from API to DB and back.

Step 7

Implement role-based access control (RBAC) — define roles: owner, admin, member, viewer. Create a middleware that checks the user's role in the current org before allowing actions. Owners can delete orgs, admins manage members, viewers can only read.

Step 8

Full production deploy — Hetzner VPS with Nginx, SSL, PM2 for the app, Redis for queues + caching, PostgreSQL for data. Set up pm2 ecosystem.config.js with both your API server and queue worker processes. You now have a production SaaS
